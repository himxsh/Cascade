## Fixed in this branch

### Installation claim was an IDOR

`user_may_claim_installation` treated a valid setup `state` as authorization. Any signed-in user can mint that state from `/api/me` and pair it with another `installation_id`.

- A user-account installation is claimable only when GitHub's `account.id` equals the signed-in `github_user_id`.
- An org installation is claimable only when that id is in `GET /user/installations` for the OAuth token stored on the session, and the signed state matches.
- The GitHub user access token is stored on the `sessions` row (column added for existing databases). It is not returned by `get_session_user` or `/api/me`.
- When the GitHub App is not configured, a real user or any `VERCEL` runtime cannot adopt a client-supplied installation id. Local `CASCADE_DEV_LOGIN` still can, so the dashboard harness keeps working.
- `CASCADE_DEV_LOGIN=1` is ignored when `VERCEL_ENV=production`.

### Mock repos collided with real webhook deliveries

Mock workspaces shared `github_repo_id` 1001 and 1002 and the names `acme/analytics` and `acme/metrics-dbt`. `lookup_repo` fell back from id to name, so a real delivery for repo 1001 named `acme/analytics` was treated as the mock. `adopt_installation` also seeded those fake rows onto a real install.

- Mock repo ids are now negative and per installation (`installation_id * 10 - slot`).
- An explicit `github_repo_id` matches that id only.
- Adopting a real installation does not seed mock repos.
- The next dashboard or login load rewrites leftover positive ids on mock installations (the old 1001/1002 rows).
- A duplicate webhook insert (two requests passing the SELECT) returns `duplicate` instead of 500 when the error is a unique violation.

### `issue_comment` installed the pull request and ran it with secrets

`.github/workflows/cascade.yml` checked out `refs/pull/N/head` and ran `pip install -e .` on `issue_comment`. That event keeps repository secrets and `contents: write`. A fork `pull_request` does not. Commenting `/cascade stack` would have executed the PR's `cascade` package.

`issue_comment` now checks the PR out as data and installs from `./trusted-cascade`, a checkout of the default branch. `actions/checkout` rejects a `path` outside the workspace, so this is not `$RUNNER_TEMP`. Checkouts set `persist-credentials: false` so the job token is not left in `.git/config`. The same flag is on the customer template (`cascade/templates/github-cascade.yml`, `examples/github-action/cascade.yml`, `frontend/public/cascade.yml`) and on `cascade-migrated.yml`. Those customer workflows still install the pinned `git+https://github.com/himxsh/Cascade.git@74e491aa…` package, which is the trusted CLI.

### Config and run ids could read outside the repo

`load_config` accepted `urn_files` and `models_dir` values such as `../.git/config`. `resolve_model_path` would then hand that file to the rewriter. Combined with a checkout that had persisted credentials, the job token could land in a prompt or a remediation commit.

- Config paths must be relative, must not contain `..` or `.git`, and the resolved file must stay under the repo (or under `models_dir` for an absolute path passed on the CLI).
- `CASCADE_RUN_ID` is stripped to `[A-Za-z0-9._-]` and `write_run_audit` refuses a directory outside `cascade/runs/`.
- Hosted `run_apply` writes its audit under the temp directory. Vercel's cwd is read-only outside `/tmp`.

### Request handling

- `_safe_next` and `SignIn.tsx` allow a single leading slash and a limited character set. `//host` and backslash forms no longer redirect off the site.
- Static files use `Path.relative_to` against the bundle root. A prefix check (`/static` vs `/static-evil`) is gone.
- CORS no longer allows `https://*.vercel.app` with credentials. `vercel.app` is a public suffix. SameSite=Lax already withheld the cookie on cross-site XHR; the regex was still the wrong allowlist. `CORS_ORIGINS` and `PUBLIC_BASE_URL` still work.
- `parse_changes_text` turns invalid JSON into `ValueError`, which `/api/run` maps to 400.
- A fine-grained lineage error retries `GET_DATASET` without that fragment for that call only. The old process-global latch turned the fallback on for every later dataset.

### `pip install cascade-bot` does not provide `cascade setup`

PyPI `cascade-bot` 0.1.0 (the only release) has `cascade init` and `cascade doctor`. It has no `setup` subcommand. `setup_cmd.py` on PyPI is 3.6 KB; on main it is about 15 KB. The version was never bumped, so that upload cannot be replaced.

This repo is now 0.1.1. The README install blocks use

```bash
pip install "cascade-bot @ git+https://github.com/himxsh/Cascade.git"
cascade setup
```

until 0.1.1 is published. A local `pip wheel` of this tree succeeds with the in-tree `cascade.build_meta` backend. An editable `pip install -e '.[ui]'` into `.venv` succeeded as well.

The marketing chip (`frontend/src/site.ts` `PIP`) still says `pip install cascade-bot`. That string is what the site should show after the PyPI publish. It is wrong until then. See "Not fixed".

## Checked and left as-is

### Webhook signatures

`api/webhook.py` requires `GITHUB_WEBHOOK_SECRET`, uses HMAC-SHA256 over the raw body, and compares with `hmac.compare_digest`. A missing secret is 503. A bad signature is rejected. Tests cover missing secret, missing header, and a bad signature.

### SQL injection

Queries use `?` placeholders. Postgres rewrites them with `qmark_to_percent`. No query concatenates request input into SQL.

`qmark_to_percent` replaces every `?`, including one inside a string literal, and a `%` already in the SQL would be interpreted by psycopg. Current statements have neither. `split_sql_statements` splits on `;` the same naive way and is only used for the schema script.

### Secrets in the repo

No `ghp_`, `github_pat_`, or private-key blocks in tracked source. `cascade/runs/` is gitignored.

### Session and token storage

Session ids and the GitHub user access token are plaintext in the database. The cookie is `httponly` and `SameSite=Lax`, and `secure` follows the request. Encrypting the token column would need a key-management story this repo does not have. The token exists so org install claims can call GitHub as that user.

OAuth still requests `scope=read:user`. Org claims call `GET /user/installations` with that token. That endpoint works for a GitHub App user access token and fails for a plain OAuth App token. On failure the setup route redirects to `installation_forbidden` (fail closed). Confirm production `GITHUB_OAUTH_CLIENT_ID` is the GitHub App's client id. Personal installs still match on `account.id` and do not need the list.

### Same-repo `pull_request` still installs the PR

`fixture-ci` and the non-comment `pr-impact` job still `pip install -e .` from the checkout. Fork pull requests do not receive secrets, and GitHub downgrades `GITHUB_TOKEN` to read-only. A same-repo PR is opened by someone who can already push. That dogfood path is unchanged. `persist-credentials: false` is set so the token is not written into `.git/config`.

### `cascade-migrated.yml`

The workflow checks out the merged `cascade/remediation/*` branch and runs it with DataHub secrets. Merging a bad PR onto that branch name runs that code. Only `persist-credentials: false` was added.

### Comment upsert sees one page

`find_cascade_comment` loads `per_page=100` and keeps the last matching marker. An older Cascade comment past that page is invisible, so a later run posts a second comment. Not changed.

### `commit_files_to_branch` force-updates the remediation ref

That is how `/cascade stack` refreshes an existing branch. Left as-is.

### Reviewer requests

`request_pr_reviewers` still sends DataHub corpuser handles to the GitHub API. The comment body no longer lists them (commit `2417351`). Invalid handles are swallowed. Not changed.

### Real installs have an empty repo list

Phase 7 does not mint an installation token or list the installation's repositories. After a real connect the dashboard is empty until that sync exists. The UI already has an empty state. Seeding `acme/*` onto the real install was the bug, not the empty list.

### libSQL transactions

`LibsqlConnection.commit` and `rollback` return immediately. Each statement is its own HTTP call, so a multi-statement write can commit partway. Postgres and sqlite use real transactions. Not changed.
